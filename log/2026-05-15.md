## Pods

This is the big one. A big one? The big one. We'll keep the first pass real tight: build the primary pod, mount the pvc, then we'll let the PG image's entrypoint do the bootstrap. *Eventually* we're going to want to move to init containers for replicas (and primaries, I suspect). Replicas, sync replication, config -- all that jazz we'll do ... later.

## Again with the decisions already

1. Image. We *must* pin the version. We can't use `:latest` in an operator. We'll hardcode it.
1. Bootstrap strategy
    * Easy: let PG do the bootstrap. If PGDATA is empty, it runs initdb and creates the user
    * More learnings: write our own initContainer

    We're going to go the _easy_ way here -- we'll get to init containers later anyway.

1. PGDATA layout. We can't mount the PVC at `/var/lib/postgresql/data` because there are other files there. The standard workaround is that we'll set `PGDATA` to a a subdirectory and the image will create that on the first run. This stuff is in the PG image's README, so I'll not linger.

1. Per-pod DNS. We're going to need a hostname and a subdomain. We can calculate both.

1. Labels must include role

1. Probes. Most PG operators skip liveness probes, but keep a readiness one. We'll skip startup for janky-PG atm.
    During recovery, restoration, or vacuum, postgres can be unresponsive in ways that doesn't equal death. A liveness probe would kill the pod mid-recovery, and we'd loop. Either omit, or set a very generous timeout. We'll skip this one.

Let's wire it up! You know the drill by now. Pods are fairly large, so I'll just paste the final shape and you can go look at the code if that strikes your fancy:

```go
func InstancePod(pg *dbv1alpha1.PostgresCluster, idx int32, role string) *corev1.Pod {
	labels := labelsForPg(pg)
	labels["role"] = role

	return &corev1.Pod{
		ObjectMeta: metav1.ObjectMeta{
			Name:      podName(pg, idx),
			Namespace: pg.Namespace,
			Labels:    labels,
		},
		Spec: corev1.PodSpec{
			Hostname:  podName(pg, idx),
			Subdomain: serviceName(pg),
			Volumes: []corev1.Volume{{
				Name: "data",
				VolumeSource: corev1.VolumeSource{
					PersistentVolumeClaim: &corev1.PersistentVolumeClaimVolumeSource{
						ClaimName: pvcName(pg, idx, "data"),
					},
				},
			}},
			Containers: []corev1.Container{{
				Name:  "postgres",
				Image: "postgres:18.4",
				Ports: []corev1.ContainerPort{{
					Name:          "postgres",
					ContainerPort: 5432,
					Protocol:      corev1.ProtocolTCP,
				}},
				EnvFrom: []corev1.EnvFromSource{
					{
						SecretRef: &corev1.SecretEnvSource{
							LocalObjectReference: corev1.LocalObjectReference{Name: secretName(pg)},
						},
					},
				},
				Env: []corev1.EnvVar{
					{
						Name:  "PGDATA",
						Value: "/var/lib/postgresql/data/pgdata",
					},
				},
				VolumeMounts: []corev1.VolumeMount{{
					Name:      "data",
					MountPath: "/var/lib/postgresql/data",
				}},
				ReadinessProbe: &corev1.Probe{
					ProbeHandler: corev1.ProbeHandler{
						Exec: &corev1.ExecAction{Command: []string{"pg_isready", "-U", "postgres"}},
					},
					InitialDelaySeconds: 5,
					PeriodSeconds:       5,
				},
			}},
		},
	}
}
```

## Replicas

A replica has a different life cycle than a primary. To become a working standby and not "another primary", it must:

1. Wait for the primary to be reachable and accepting connections
1. Run pg_basebackup against the primary, which populates the data directory with a base backup. Here, you could conceivably use something like pgbackrest instead and restore from that but this is janky-pg, and it's also ... some ways off.
    While the backup is running, the replica streams WAL too
1. mark the data dir as a standby. This is done with `touch standby.signal` inside `$PGDATA`. If postgres sees that, it starts as a standby instead.
1. Configure primary_conninfo so that the standby knows where to stream WAL from. We write it to postgresql.conf for our VMs, but some like to write `postgresql.auto.conf` instead -- it doesn't matter. `postgresql.auto.conf` takes precedence if both have entries.
1. start postgres

We run our databases on VMs, where "poke at file" is easy. In k8s land it's less easy. We'll do this, though: first we'll run an init container: empty pg_basebackup workflow. It runs once and exits 0. Then we'll enter the main container. Since the data directery exists and has a `standby.signal` (our init container wrote that), postgres comes up as a standby.

Both images (primary and replica) are the same. That's important.

There's a coordination problem, though. The replica's init container needs to wait for the primary to be reachable. Options:

1. A loop in the container that polls primary DNS + `pg_isready` until it works.
1. our operator gates Pod creation -- we only create replicas after primary is `1/1 Running`. More operator code, _and what happens if the primary crashes after a replica starts_?

We'll use the first option. It's janky-pg, and it's easier. We can do something else further down the line.

And there's an auth problem. Postgres uses `scram-sha-256` for non-local connections (gone are the days of `md5`) -- pg_basebackup from a replica pod is a remote connection. We need to allow the replica connection in the `pg_hba.conf`. pod IPs are dynamic, but we can match on `host replication all 0.0.0.0/0 scram-sha-256`. The replica also need credentials.

This is a lot.

We'll just skip most of that for now. `POSTGRES_HOST_AUTH_METHOD=trust` disables all auth for non-local connections. *Don't use this in prod.* Later on we can mount a custom `pg_hba.conf` via a ConfigMap. We can also add mTLS. Later.

Our goal is quorum sync mode, but for now we'll be happy with async replicas. Quorum requires that replicas set an `application_name`, and the primary must be told the list of standby names. This list would change every time `spec.replicas` change. There's a few ways we can skin this, but we'll touch on that when we reach for quorum sync, not now.

At this point I'll probably start pasting huge blocks of code. You (me) have followed me for this long, and you know what to do. Here's the outline:

1. InstancePod needs an init container when `role == "replica"`
    * the init container runs a small script that waits for the primary to be reachable
    * it then runs pg_basebackup
1. Primary and replica need `POSTGRES_HOST_AUTH_METHOD=trust` in their env, for now.
1. Reconcile loop needs to create replicas in addition to the primary.
1. Primary stays idx = 0, role = "primary"

Some design questions we'll make along the way:

1. Where does the init container script live?
1. Init container image -- same postgres:18.4 or a busybox + pg client sidecar?
1. Do we create PVCs + replica Pods in the same loop, or do we create the PVCs first, then the latter?

```go
func initContainersFor(pg *dbv1alpha1.PostgresCluster, role string, env []corev1.EnvVar) []corev1.Container {
	var initContainers []corev1.Container
	if role == "replica" {
		// TODO: this assumes that idx 0 is always the primary. This is not true
		// after a failover. We'll deal with that later.

		primaryHost := hostName(pg, 0)
		script := fmt.Sprintf(`
	set -e
	until pg_isready -h %s -U postgres; do
    echo "waiting for primary..."
    sleep 2
	done
	if [ ! -s "$PGDATA/PG_VERSION" ]; then
    pg_basebackup -h %s -D "$PGDATA" -U postgres -X stream -R -P
	fi
	`, primaryHost, primaryHost)

		initContainers = append(initContainers, corev1.Container{
			Name:    "bootstrap",
			Image:   PostgresImage,
			Command: []string{"sh", "-c", script},
			Env:     env,
			VolumeMounts: []corev1.VolumeMount{{
				Name:      "data",
				MountPath: "/var/lib/postgresql/data",
			}},
		})
	}

	return initContainers
}
```

Other than that, it's fairly straight forward. The `-R` is neat, the long form is `--write-recovery-conf`, it auto-configures the new data directory after the basebackup. It creates the `standby.signal`, and it also adds a `primary_conninfo` to `postgresql.auto.conf`. `-P` is just progress reports.

One snag though: `-R` sets a generated name, so we can't use it for quorum sync. Or we can, we just have to set the generated name correctly.

More snags, however: `POSTGRES_HOST_AUTH_METHOD` doesn't actually work for replication. What the env var does is set `host all all all trust` in the pg_hba -- anyone can connect to anything. Except replication. Replication is a special database, so we need to update our pg_hba with `host replication all all trust` to get it working.

We'll do that tomorrow, it's gonna require a configmap. For now, we can hack the pg_hba file by getting a shell into the primary, adding the line to pg_hba, then `psql -U postgres -c 'SELECT pg_reload_conf();'` -- after that, our replicas are streaming from the primary.
