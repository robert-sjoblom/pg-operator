## Day 0

I need to learn more k8s. Or, rather -- more about extending core kubernetes functionality. I suspect there's some hidden power in writing your own stuff, that I can unlock things that I may need or want, or something that can help me in my day-to-day @work.

That said. I'm not a complete novice when it comes to kubernetes. I can ruin a deploy as well as the next schmoe, and I know how to bring stuff down real quick if you ask me. I know what Deployments and StatefulSets are (at least on the surface), and I know what etcd does. So we'll start here: writing our own operator. We'll learn more along the way.

At work, we use Harvester. We run PG on VMs, which is very nice but deploys take a while. Getting new VMs is easy: we do IaC, so we just do an edit in a jsonnet file:

```json
clusters = [
    ...,
    { id: x + 1 },
]
```

which you can override in various ways (more disk, more cpu cores, more memory, what OS etc). You generate the jsonnet manifests, merge your PR, and then you wait for the reconciliation loop. Eventually, you have your new VM (well, you have 3 because we only run HA setups. And you get a new HAproxy too, and some other stuff).

Then you turn to ansible and deploy _all the rest_ you need. Postgres, SELinux stuff, DNS, certificates, pgbackrest, journald, OTEL stuff. Etc, etc, etc. It takes a while. Not only that, but it's also _boring_. It's watching paint dry.

There's potential in writing an operator here, too. The ansible stuff? Some of that, we can solve with an operator. When a VM crashes and returns in a broken state, we could perhaps just delete the machine and wait for reconciliation to bring it back and the operator would install our replica (because we don't throw away primaries, right?) properly. That'd be nice.

But we'll start here. By writing our own thing. It's going to be terrible and we'll learn a lot at the same time.

```bash
2026-05-13T21:03:30+02:00       INFO    Starting EventSource    {"controller": "postgrescluster", "controllerGroup": "db.robert-sjoblom.dev", "controllerKind": "PostgresCluster", "source": "kind source: *v1alpha1.PostgresCluster"}
```

This is the operator core. The controller-runtime opens a _watch_ against the API server for our `PostgresCluster` objects. Behind the scenes:

1. It calls `LIST` on `/apis/db.robert-sjoblom.dev/v1alpha1/postgresclusters` to get all existing objects
1. It opens a `WATCH` connection, which is basically just a long-lived stream, to receive `Added`, `Modified`, `Deleted` events (for the `PostgresCluster` kind)
1. The objects are added to an informer store, which is an in-memory cache.
1. Every event causes the object's *namespace* to be pushed on to a work queue (done by the informer after cache has been updated).

We never read from the API server, we always reads from the cache. Writes go through the API server, and watches keep the cache fresh.

We then get lines for "I'm starting a new controller of controllerKind `PostgresCluster`, and a new worker from that. The controller runs X goroutines, here 1 -- our `Reconcile` is single-threaded per controller. You can run more, but it's tricky! We'll ... maybe get there, I guess.

---

A bad sketch:

[API server] -> WATCH events -> [informer/cache] -> namespace -> [workqueue] -> pop [Reconcile] -> write to API server

the API server produces WATCh events, that are saved in the informer. The informer calls the registered event handlers, which put the namespace on the workqueue. Your reconciler then pops keys.

The *cache-then-queue* ordering is guaranteed. By the time our reconciler pops a key and calls `Get` (on the informer store) the key is guaranteed to be there -- the same is not true for writes, writes do not show up in the cache until the watch event for them comes back. makes sense, really.

The queue is keyed *and deduped*. It's not a kafka stream where each event is handled in order. Several updates becomes _one_ entry in the queue.

We'll get more into the queue and events, watches and registering `Watches` and `Owns` and so on later.

### Updating our CRD

We want our users to specify the number of replicas they want. We want to require a minimum of 2, and a maximum of 10. There's a footgun here:

```go
// PostgresClusterSpec defines the desired state of PostgresCluster
type PostgresClusterSpec struct {
	// Number of standby replicas, in addition to the primary
	// +optional
    // +kubebuilder:default:=2
    // +kubebuilder:validation:Minimum:=2
	// +kubebuilder:validation:Maximum:=10
	Replicas int32 `json:"replicas,omitempty"` // K8s API conventions prefer fixed-width
}
```

Can you spot it? It's sneaky!

It's because of Go's zero values (imo the worst design decision in the language). `omitempty` + `zero value` + `default` = footgun. Here's what happens if a user _explicitly_ writes `replicas: 0`: *The user gets `2` replicas.*

What?

1. client-side marshaling drops the field because 0 is the Go zero value and `omitempty` is set
1. The apiserver sees no field, applies the default -> `replicas: 2`
1. Our `Minimum: 2` validation never fires, because the user's `0` vanished

Sneaky, sneaky.

What we *want* to do is either:

1. Pointer + `omitempty`: `*int32` -- this distinguishes "user didn't set it" from "user set it to 0"
1. drop `omitempty` on the value type.
1. Make it required, no default.

If we run `make manifests`, our postgresclusters.yaml updates:
```yaml
            properties:
              replicas:
                description: Number of standby replicas, in addition to the primary
                format: int32
                maximum: 10
                minimum: 2
                type: integer
            required:
            - replicas
```

```bash
      {"apiVersion":"db.robert-sjoblom.dev/v1alpha1","kind":"PostgresCluster","metadata":{"annotations":{},"name":"minimal-cr","namespace":"default"},"spec":{"foo":"hello world!"}}
  creationTimestamp: "2026-05-13T19:39:02Z"
  generation: 1
  name: minimal-cr
  namespace: default
  resourceVersion: "16330"
  uid: 0006eec8-df70-4d1b-bede-da36e0a7272d
spec: {}
```

The apiserver prunes unknown fields, that's why our `spec` field is empty. `foo` is not part of it any longer. If we try to applly the old CR: `strict decoding error: unknown field "spec.foo"`. The _annotation_ is not pruned, though.

Here, we could think that `kubectl annotate postgrescluster minimal-cr touched=now --overwrite` would explode in our faces. How can we annotate an invalid CR?

We can (try it out), because of _CRD validation ratcheting_. On update, the apiserver validates _only the parts of the object the user actually changed._ Fields that already violate the schema are tolerated, as long as the new update doesn't touch them. Kube allows people to tighten schemas without breaking the ability to manage pre-existing, non-conforming objects.

Let's break it:

```bash
robert.sjoblom ~/9th/pg-operator (main)$ kubectl patch postgrescluster minimal-cr --type=merge -p '{"spec":{}}'
The PostgresCluster "minimal-cr" is invalid: spec.replicas: Invalid value: 1: spec.replicas in body should be greater than or equal to 2
```

We should keep this in mind in the future: *just because our current schema says a field is required, doesn't mean all the objects in etc will have that field.* Our reconcilers need to be defensive.

In good, production-ready code, you'd bump the CRD version instead (ours is `v1alpha1`, we'd bump to `v1alpha2` for instance).

Let's edit our minimal-cr and apply it:

```yaml
spec:
  replicas: 2
```

```bash
robert.sjoblom ~/9th/pg-operator (main)$ kubectl apply -f cr/cr.yaml
postgrescluster.db.robert-sjoblom.dev/minimal-cr configured
```
