# Day 4

## What's in a ~~name~~ ConfigMap anyway?

We've gotten pretty far without even creating a configmap, but that's mostly because this isn't a real project. A real project would have _so much stuff_ in there already.

But, we can't avoid it any longer. We need to run an init script on bootstrap. Remember the hack I had to do to [get replication working](https://github.com/robert-sjoblom/pg-operator/blob/main/log/2026-05-15.md)? Well, it wouldn't be much of an operator if it couldn't solve that properly -- I'm not waiting hand and foot on random deploys in the middle of the night to shell in and run random scripts.

We need something that codifies our pg_hba setup. A few ways to skin this:

1. We could do custom postgres images
1. We could do an init script

Custom images doesn't really work that well once we start adding authentication and stuff though, so we'll go with option number 2.

We'll create a ConfigMap like so:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: <cluster>
  namespace: default
data:
  00-replication-hba.sh: 'echo "host replication all all trust" >> "$PGDATA/pg_hba.conf"'
```

We'll mount this on the primary with DefaultMode `0755`. On startup, when `PGDATA` is empty, the pg image runs any scripts in `/docker-entrypoint-initdb.d/`. We need this script to run first, so we'll name it `00-`, which is fairly standard -- the scripts are run in alphabetical order. It will also let us add more scripts ordered properly.

You might be wondering, why only primaries?

Because replicas don't run init scripts -- their data dirs are populated by `pg_basebackup` and if the primary's pg_hba looks a certain way well... then the replica's does, too. This also solves our future failover scenario -- pg_hba is already wired!

## Last piece of the ~~pie~~ machinery

As if. We've some ways to go, but we're nearly done for the v1 version. The goal of v1 was a cluster with quorum sync. Right now, our cluster is in async mode. To reach quorum sync we need two pieces:

1. deterministic `application_name` per replica
    Synchronous replication matches by name, so each replica needs a *known* name. `-R` doesn't cut it.
1. `synchronous_standby_names` on the primary.
    Our primary needs `synchronous_standby_names = 'ANY 1 (minimal-cr-1, minimal-cr-2)'` in the postgresql.conf (or the auto conf), then you do a `SELECT pg_reload_conf()` for the change to take effect.

The way I see it, we have one option for now: we extend our bootstrap with another script `01-sync-rep.sh`. Primary reads it at start. Quick, dirty, and a handful of drawbacks: it doesn't react to `spec.replicas` changes (going from 2 -> 3 would leave the new replicas as async forever). It also can't react to any failover that could happen. Right now, this is the correct choice: we're going to start the next leg of our journey (v2) with dynamic sync names (query the current names, run ALTER SYSTEM SET, reload conf)... later.

These are just changes to our configmap and pg_basebackup script, fairly easy. Quoting tripped me up, because `minimal-cr-0` has dashes, and so those names must be quoted, but overall nothing to it:

```bash

# It will be overwritten by the ALTER SYSTEM command.
