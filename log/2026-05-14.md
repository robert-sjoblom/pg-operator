# Day 2

Today, we're going to write the reconciler. Not the ... entire thing, right, because that's insane. Our goal is to create a janky HA postgres cluster in kubernetes, but even that is... a *lot* of work. We'll start with the first step, not the last one.

Every reconcile signature looks the same: `func (r *YourTypeReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error)` and if you think that `Result` is anything like Rust's you'll be sorely disappointed.

* `ctx` is self-explanatory for go developers.
* `req.NamespacedName` is the namespace/name of the object we're reconciling
* `ctrl.Result` is what to do _after_ this run
* `error` if we return a non-nil error, we trigger the exponential-backoff requeue we all know and love

There are three return values we'll use:

1. `return ctrl.Result{}, nil` means "I'm done, don't requeue<sup>1</sup>. Wait for the next Watch event"
1. `return ctrl.Result{RequeueAfter: 30*time.Second}, nil` is "Check again in 30 seconds. I'm waiting on something that doesn't produce a watch event.
1. `return ctrl.Result{}, err` -- "Something went wrong. Requeue with exponential backoff." Whoever the caller is (the controller), will log the error and requeue.

## Rules

Reconcile must be *idempotent* and *convergent*. Idempotency means the same as every time you've seen it: running things twice on an unchanged world produces no change. We don't produce new pods if the right pods already exist. *Convergency* just means that each run of the reconciler takes us closer to the desired state. If we can't do everything in one call (usually the case), then we do what we can in /this/ run, we update the status, and return. The next call continues the work.

We can *never* assume "This is the first time I've seen this object" _or_ "the user just changed something." Every run is a fresh observation. Event or edge semantics doesn't matter, we only look at the _current_ state and act.

## The shape of ~~water~~ reconcilers

1. Fetch the CR. If we can't find it, it was deleted (DELETE is a watch event!). If we get an error we return the error.
1. Handle finalizers. We'll skip this for now.
1. Compute our DESIRED state from the cr.Spec field. This is a list of things that should exist -- Services, Pods, PVCs, Secrets, ConfigMaps, other CRs, etc

    * Sidenote: to the apiserver, a CR is just an object. A ConfigMap is an object, and your CR is an object. Your operator can `Create` a `Foo` CR the same way it creates a pod. Two flavors:
        1. Same binary, multiple controllers. A high-level CR creates lower-level CRs that other operators reconcile. Each operator focuses only on its own layer. c.f. `CloudNativePg` -> `Backup` chain. The `Cluster` CR's reconcile creates `ScheduledBackup`/`Backup` CRs, these are handled by separate controllers (within the same cnpg operator binary)
        1. Different binaries. Operator A creates CRs that Operator B reconciles. Built and released independently. Crossplane is a good example, communication is purely though CRs in etcd.


1. Observe ACTUAL state. List all children that currently exist, owned by this CR. This is where we hit the controller's cache.

1. Reconcile the diff
    * for each desired child that's missing -> Create
    * for each desired child that exists but differs -> Update/Patch
    * for each existing child not in desired -> Delete

1. Update cr.Status to reflect what you observed/did.

1. Return (Result, nil), which is usually `Result{}` unless we're waiting for something (rebuilding replica)

For this project, our desired state is: a headless Service, a Secret with credentials, a ConfigMap with postgres configs/scripts, a primary PVC + Pod and `spec.replicas` replica PVCs + Pods. Plus init containers on each pod that handle initial PG setup or pg_basebackup for replicas. So ... there's a lot. And our setup is _janky_.

Let's do step 1 and 2 first.

## More rules

* Always set owner references on children (`controllerutil.SetControllerReference(&cr, &child, r.Scheme)`) before creating -- this makes `Owns(...)` watches work, and gives you garbage collection
* *never* update `spec.` during reconcile. Modifying spec from inside reconcile creates a feedback loop with users editing the same object. We can only update status.
* Status updates are a separate API call. Kubebuilder set `+kubebuilder:subresource:status`, updates go through `r.Status().Update(ctx, &cr)`, not `r.Update`. This prevents us clobbering user spec edits between Get and write.

There's a `controllerutil.CreateOrUpdate` that seems fraught. For simple cases it works, but for complex cases (server-side apply, apiserver mutations, three-way merges) we'll use something else.

`RBAC` markers matter. Kubebuilder generated defaults above our `Reconcile` function, it's the `// +kubebuilder:rbac:...` comments. Every new Kind we touch needs RBAC. When we start creating Pods we'll need to add `//  +kubebuilder:rbac:groups=core,resources=pods,verbs=get;list;watch;create;update;patch;delete`. We'll absolutely forget doing this.

Our project is pretty good in that we're going to be exposed to two different things we need to keep an eye on (I do not use the word "watch" here). For instance, if we promote a replica to a primary, the current replica count changes (have: N - 1, want: N). Creating a new pod -> a WATCH event (+ more watch events for PVCs etc). If what we're waiting for is WATCH driven:
* I created a new replica Pod, I'm waiting for it to become Ready" -> watch on Pods fires when Pod's status changes, Reconcile re-runs automatically
* I deleted the old PVC and am waiting for the new one -> Watch on PVCs
* I'm waiting for the user to fix `spec` -> Watch on CR

* The Pod is running, but I need to check whether pg_basebackup is finished -> Pod state doesn't change, we have to ask postgres itself
* I started a switchover -> External state (postgres internals), not k8s
* I'm tracking replication lag and need to react if it exceeds X -> polling

## A choice

We can either create the first meaningful child: a Service, or we can jump straight to PVC + Pod for the primary. We'll go with the service, it's smaller but we'll encounter patterns we'll use everywhere.

### Why a Service?

For our specific operator, we need stable DNS. Postgres operates on hostnames; we'd need to re-bootstrap everything if it changed every time the primary pod restarted. We're not writing applications here, but eventually an app would also need a name to point at.

More decisions: headless or ClusterIp.

A headless service has no virtual IP itself, or kube-proxy load-balancing. Instead, each Pod matched by the Service's selector gets its own DNS A record at `<pod>.<service>.<namespace>.svc.cluster.local`. This is what we want for stateful workloads. It lets us reach individual pods by name. PG operators almost universally use headless Service for the cluster.

Regular ClusterIP Service has one virtual IP. Traffic is load-balanced across all pods matching the selector. We'll add two of these later, one `<cluster>-rw` and one `<cluster>-ro` -- the `-ro` will select only replicas, and the `-rw` only the primary. For our v1, one headless Service is enough.

## Even more decisions

There are only 3 difficult things in programming: Off by one errors, and naming things. Here, we're going to:

* name the Service (`metadata.name`) -- consistency is key here, because pod hostnames will live under this name _forever_. `<clusterName>` is good for now, then `<clusterName>-ro` etc later.
* namespace: always the same as the CR's namespace. Always.
* Labels. Two label concepts we do not want to conflate:
	* Labels on the service object itself, so we can find it: `kubectl get svc -l cluster=<name>`
	* `spec.selector`-labels that the Service uses to match Pods. These must match the labels we'll put on Pods later. Decide it now because we'll repeat it _everywhere_: Pods, PVCs, etc.

If we go by the k8s conventions (`app.kubernetes.io/*`):

```yaml
app.kubernetes.io/instance: <clusterName>
app.kubernetes.io/managed-by: pg-operator
```

We'll also add a `role`label that varies per pod: `role: primary` or `role: replica`. Our Service will select on `instance`.

## Divergence

There's a trap in StatefulSets that we've so far avoided, but we may want to talk a little bit about. On the surface, it looks like what we want: Pods with ordinals (`<cluster>-0, <cluster>-1` etc), stable hostnames, sticky PVCs... _However_, postgres's roles are *not* ordinal-based. In postgres, one pod is a _primary_ and another is a _replica_. Their ordinals doesn't matter but *how they start* differ. There are different bootstrap commands for postgres if it starts as a primary or as a replica. *Furthermore*, and perhaps even worse (there are other issues with StatefulSets -- config needs to differ based on role). A StatefulSet will start and shut down pods in a specific order (`-0` will start first, then `-1` and so on). Another thing StatefulSets would give us is volume-to-pod stickiness -- pod-N will always mount to PVC-N. Most postgres operators solve all this without STS, and we'll do too. More things that we can't solve in STS is stuff like updates (STS would update in ordinal number sequence, but that may mean the primary restarts first -- we don't want that), failover is trickier, the PVC layout is rigid, and you can't customize per-pod.

Modern PG operators, instead, manage Pods and PVCs directly. You'll see this when we get to it, but the tl;dr is that we get to do more coding and thinking about more things<sup>2</sup>. Fun!

## PVCs

Before we start thinking about our PVCs, we should consider what we need to achieve. We always want to map the same PVC to the same Pod. We can't use STS. We can live by the kubernetes principle `names are identity, labels are state` -- we'll name our PVCs `<cluster>-0`, `<cluster>-1` and so on, and we'll name our pods, well, `<cluster>-0`, `<cluster>-1` and so on. Stable, predictable, boring. Easy to reason about. Meanwhile, a pod's *role* (primary, replica) is a *label* on the pod. On failover, the operator (our operator) updates the label. Nothing in `metadata.name` moves.

As always, naming things pops up. We could extend `<cluster>-1-pvc`, but that doesn't really tell us what the PVC is for. Right now we're looking at a single PVC, but we'll be adding more later, and being able to discern which is which would be good. `data-<cluster>-0` and `wal-<cluster>-0` works well. Our pods (later) will be named `<cluster>-0`.
